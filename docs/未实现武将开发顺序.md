## 先辨认身份，再排批次

每批开始时以 `python tools/check_new_hero_candidates.py excel_rNNN ...` 核对**精确代码与全名**；再对照公开名单、专属战斗接线、AI、前端说明与行为场景。同名词根须列出已公开亲属，逐个辨认，不能因相似名字判为重复，也不能因来源数据或自动生成类存在便算公开。若已经公开，转为既有武将审查，不计新增；若源表行号或姓名改变，先重做门禁及设计基线。

## 每批完成条件

1. 源表原句与保存问卷逐个核对；独立解释先同步到设计 JSON 与 XLSX，再看该将战斗/AI/测试代码。未回答的具体歧义记录推断和反证，不用通用模板问题。
2. 按技能逐项核对声明、付款、合法目标、行动窗口、连锁、破魔与受影响者反应、位移后效、状态到期、召唤/死亡/多格身体；同步标准、简单、倾向 AI 及玩家预览/点击。
3. 定向行为场景覆盖设计边界，并给用户一条只运行本批的审计命令，完整日志写到独立目录；多个定向场景类可在 `--regression-filter` 中用逗号连接筛选词。助手只做静态语法和文档检查，不运行动态测试或 AI 对局；用户返回结果后先修失败再开发下一批。
4. 完成后报告：本批新公开人数、累计公开/388、仍未实现/388、当前批次动态验证状态。源设计已锁但未完成接线的武将单独列为待实施，不混入累计。
