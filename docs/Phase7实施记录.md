# Phase 7 实施记录

## 阶段目标

让 2～4 名真人能够可靠完成长期战役；缺席、断线、服务重启或版本升级不再要求所有人同时在线，也不需要人工修改存档。

## 实施顺序

1. P7.1 月度提交、房主截止与缺席代理。
2. P7.2 同势力多人官职、交接与临时代管。
3. P7.3 加入码、身份、重连、战斗中断恢复与归档。
4. P7.4 版本化迁移、备份、审计与管理修复。
5. P7.5 正式环境安全、限流、隐私和可观测性。
6. P7.6 无障碍与 2～4 人完整战役走查。

## P7.1 规则

- 真人成员可以独立进入、恢复、查看战役并提交自己权限内的行动，不再要求所有初始真人同时在线。
- 每个战略月份、每名初始真人只有一个公开提交状态：`drafting`（拟定中）、`ready`（已提交）或 `proxy_ai`（本月 AI 临时托管）。AI 初始席位不进入真人提交统计。
- 玩家把本月标记为已提交后，不能继续新增或替换行动；在房主结算前可以撤回为拟定中。撤回不会删除已排队行动。
- 房主调用推进时自动把自己标记为已提交；其他真人必须已经提交或处于本月临时托管状态。
- 房主关闭本月截止前必须已经提交自己。只有当前确实离线、仍处于拟定中的真人会被标记为 `proxy_ai`；仍在线但未提交的真人不能被房主强制托管。
- 临时托管只对当前月份生效。该势力已经提交的合法行动先结算，AI 再使用剩余军令按同规则补足本月决策；成员身份、官职和下一月控制权不改变。
- 被托管玩家若在房主推进前重新上线，可以把状态改为已提交并取回当月控制；已经开始月结后不能中途改写。
- 本阶段不增加真实时间自动截止、不永久踢出成员、不改变官职、不允许房主托管仍在线玩家。

## P7.1 验收

- 两名真人不同时在线时仍可分别进入、下令和提交。
- 未提交的在线成员会阻止月结，并获得明确名单与原因。
- 离线未提交成员可由已提交的房主关闭截止并获得仅当月 AI 代理；其既有行动先结算，AI 只使用剩余军令。
- 已提交成员不能继续排队，撤回后可以继续；服务重启后状态仍保存在数据库。
- 新月份自动回到拟定中，上一月代理不延续。
- 行为测试覆盖正常提交、在线阻塞、离线托管、重新上线取回、权限拒绝和单人兼容。

- 战役恢复已改为异步：锁定后的真人成员无论其他初始玩家是否在线，都能独立进入、查看和下达自己权限内的军令。
- 新增按战役、真人和月份持久化的 `drafting / ready / proxy_ai` 状态，以及提交、撤回和房主关闭截止接口。
- 已提交或当月被托管的成员不能新增、替换军令；撤回后立即取回控制，既有队列保持不变。
- 房主推进会自动提交自己；在线未提交者继续阻止结算，离线未提交者只能由已提交房主关闭截止后获得当月临时托管。
- 月结顺序保持“真人既有队列 → 剩余军令 AI → 月度结算”，临时托管不修改成员、势力或官职，并在新月份自动回到拟定中。

## P7.2 规则

- 固定十二月战役仍为 2 个主要势力，但真人容量从“每势力一人”扩展为 2～4 人、每势力最多 2 人；默认加入优先平衡两方，也可明确选择加入房主势力进行合作。
- 每名真人仍只控制一名英灵。每个势力第一名真人控制主公，第二名真人初始控制主城城主，双方共享势力资源与 4 点月度军令，但各自只能使用本人官职权限。
- 同势力第二名真人不能直接覆盖现任真人主公。正式官职交接必须由当前持有人发起、接任者确认；如果双方都有官职，则交换各自的英灵与职位，不制造额外职位。
- 真人主公可以提出撤换非主公真人官职，但在任玩家确认前权限不变；确认后该英灵仍由原玩家控制并保持仕官，职位成为空缺。主公职位不能通过普通撤换直接变为空缺。
- 交接双方有待结算军令，或相关成员已经提交/被托管时，不能确认官职变化；请求跨月自动过期，避免旧授权污染下一月。
- 战役房主与势力主公是两个不同概念：只有战役房主发起月度结算；具体游戏行动继续由当前官职授权。

### P7.2.3 空缺职位当月临时代管与权限审计（已完成，2026-08-03）

- 当前真人主公可以把本势力一个非主公空缺职位授权给同势力另一名仍在拟定中的真人；主公不能授权自己，职位或玩家同一时间最多存在一条有效代管。
- 代管不会给英灵制造第二个正式任职，而是把空缺职位标记为 `temporary_player`；既有官职解析与军令权限管线直接以代管玩家为控制者，不增加绕过权限的特殊行动入口。
- 授权记录持久化保存战役、月份、势力、职位、授权主公、代管者、状态及开始/结束时间；战情室公开当前代管和最近结果，并明确显示“临时代管”。
- 授权主公、现任主公或代管者可以提前结束；该职位仍有代管者签发的待结算军令时禁止结束，避免已经排队的军令失去签发身份。
- 临时代管仅持续当前战略月份。月结先执行并归档该月军令，再自动结束旧月份代管并把职位恢复为空缺；官职与英灵系统重建不会在月内误删代管控制。
- 已结算战役、非主公、跨势力成员、本人授权、非空缺/主公职位、已提交或被代理的成员均不能新建代管。
- 领域、HTTP 与前端行为测试覆盖授权、权限签发、禁止带单撤销、越权拒绝、自我授权拒绝、月初自动到期、审计公开和前端操作入口；完整回归 702 项通过，8 项按环境跳过。

## P7.3 规则与实施顺序

- 战役邀请只用于大厅加入新成员，不是成员恢复凭据。已加入成员在换设备、浏览器存储丢失或重新登录后，必须通过账号成员关系找回战役，不需要旧加入码。
- 房主可以在大厅明确撤销当前加入码，撤销后旧码立即失效；重发必须生成不同的新码并重新开放邀请。战役锁定后邀请自动关闭，不能再重发。
- 战略格子战必须绑定战役、战斗记录和参与账号。浏览器刷新、临时断线或服务重启后，原参与者应回到同一战斗检查点；不得重复扣除战略资源、重复生成战斗或重复写回战果。
- 如果战斗检查点确实无法恢复，系统只能从战役中保存的不可变战前快照安全重开，并明确告诉玩家发生了什么；不能悄悄丢弃或自动判胜负。
- 归档战役继续绑定原账号并可只读恢复复盘，但不能重新开放邀请、下令或再次结算。

### P7.3.1 邀请撤销/重发与账号身份恢复反馈（已完成，2026-08-03）

- 战役锁定时关闭邀请；成员列表与战役卡明确区分“邀请开放 / 已撤销 / 战役已锁定”。
- 登录后的战役列表明确说明当前账号可直接恢复自己的战役，不把加入码误写成恢复凭据。
- 邀请状态以 `open / revoked / locked` 对外公开；只有大厅中的房主可以撤销或重发，重发必定生成新码，锁定后不能重新开放。
- 行为测试覆盖非房主拒绝、撤销旧码、重发换码、锁定关闭邀请，以及使用同一账号的新登录会话直接找回并进入原战役；完整回归 702 项通过，8 项按环境跳过。

- 战略战斗创建并写入战役后立即建立检查点；房间读取、真人行动、AI 推进、投降和结算出口会刷新检查点。普通自定义对战不产生战略检查点。

## P7.4 规则与实施顺序

- 战略数据库结构版本与世界存档格式版本分别管理；共享 SQLite 中不能使用会与账号、历史等模块冲突的全库版本号。
- 迁移必须按顺序、事务化、可重复启动且只应用一次。旧版本只能通过已登记步骤向前迁移；高于当前服务支持版本的存档必须明确拒绝，不能猜测性读取或降级覆盖。
- 每次存档格式迁移必须保留迁移前原始载荷、前后摘要、版本和时间；整库备份与恢复演练在此基础上单独实现。
- 备份、诊断和管理修复都必须有受限入口、明确预检、不可变审计与可验证结果；不能提供任意 SQL 或静默修档能力。

实施顺序固定为：

1. P7.4.1 存档/数据库版本与幂等迁移。
2. P7.4.2 自动备份、保留策略与恢复演练。
3. P7.4.3 操作审计与完整性诊断。
4. P7.4.4 受限管理修复、故障手册与完整走查。

### P7.4.1 存档/数据库版本与幂等迁移（已完成，2026-08-03）

- `WorldState` 现在写入 `save_format_version=1`；所有世界读取统一先经过纯数据迁移管线，缺少版本的既有存档按版本 0 升级到版本 1。
- SQLite 使用战略模块私有的结构迁移账本，当前结构版本为 2；每一步保存版本、名称和执行时间，重复启动不会重复执行。
- 存档迁移在同一事务内规范化并回写；独立账本保存战役、起止版本、迁移前完整 JSON、前后 SHA-256 摘要和时间，既可证明幂等，也保留单存档回滚来源。
- 非法、负数或高于当前支持版本的存档返回明确冲突错误；服务不会尝试读取、覆盖或产生迁移记录。
- 行为测试覆盖服务重启后旧存档自动升级、再次重启不重复迁移以及公开世界版本稳定；领域测试覆盖结构账本、迁移载荷/摘要、纯迁移幂等和未来版本原样拒绝。
- 战略专项 179 项通过；完整回归 708 项通过，8 项按环境跳过。

P7.4.1 已完成；下一实施单元为 P7.4.2“自动备份、保留策略与恢复演练”。

### P7.4.2 自动备份、保留策略与恢复演练（已完成，2026-08-03）

- 备份通过 SQLite 在线备份 API 创建一致的整库快照；账号、会话、战役、行动、战斗检查点和对局历史使用同一数据库时不会被拆成无法对应的局部导出。
- 数据库结构迁移前和首次旧世界存档迁移前自动创建快照。备份失败会阻止对应迁移，不能在没有安全快照的情况下继续改写旧数据。

## P7.5 规则与实施顺序
