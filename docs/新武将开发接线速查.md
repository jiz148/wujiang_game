# 新武将开发接线速查

这页是当前 OOP 结构的新将入口索引。常规新将先读本页、待开发顺序和该将源文/设计档，再按实际机制打开对应对象；无需每次通读《架构分层说明》。涉及新共享接口、对象归属不清或调用链变化时，再读架构文档的相关章节并追踪实际调用者。

## 开始前

1. 按《未实现武将开发顺序》确定精确行号，运行 `python tools/check_new_hero_candidates.py excel_rNNN`。已公开将不重复新增。
2. 只依据 `excel_roster_data.py` 的源行、通用规则、已保存问卷答案，先锁 `武将设计思想.json`、`武将说明.md`，再把设计同步到 `武将实现问题清单.xlsx`。此时不要用已有实现或测试反推设计。
3. 把源文拆为声明与选取、费用与次数、命中与连锁、状态/死亡/复出、AI 决策、网页选择和可观察日志。只打开本将需要的现有对象与共享接口。

## 代码归属与调用路径

| 需要实现的内容 | 首选位置和入口 |
| --- | --- |
| 源身份、基础数值、技能/特性原句 | `src/wujiang/tactical/heroes/excel_roster_data.py`；来源不等于公开 |
| 本将规则、收益与目标判断 | `src/wujiang/tactical/heroes/<hero>.py` 的 `Skill`、`Trait`、`Status`、`HeroAIPolicy` 对象 |
| 源片段到对象的装配 | `src/wujiang/tactical/heroes/kits/excel_rNNN.py` 中的 `FragmentMappedHeroKit`；特殊属性用 `HeroKit.unit_attributes` |
| 正式注册 | `kits/__init__.py` 导入列表及 `excel_roster.py` 的公开代码集合；全部接线和场景完成后再登记 |
| 目标、区域与网页预览 | 技能的 `preview`、`get_target_cells_for_payload`、`get_target_units_for_payload`；普攻特性的 `basic_attack_area_cells`、`basic_attack_payload_metadata`、`basic_attack_preview` |
| 伤害/死亡与分段连锁 | 对象回调 `on_after_damage`、`on_unit_destroyed`；需要独立连锁段时由对象调用 `queue_skill_effect_action`，不要在中央按武将编号分支 |
| 玩家在结算中选目标/落格 | 对象调用 `optional_position_choice`；共享提示由 `battle_execution.py`、`battle_presentation.py` 和网页 `vfx.js`/`battle-ui.js` 显示，增加提示类型时三路 AI 同步接入 |
| 移动费用与失败判定 | 状态/特性的 `can_use_normal_move` 负责预览与声明前的资源门禁，`on_before_normal_move` 负责已校验普通移动的付款，`on_before_move` 可取消任意已校验位移；失败的普通移动消耗机会。技能排出的后续效果保留原声明类型供连锁保护识别 |
| AI 候选和估值 | 技能对象 `ai_payload_value`、`ai_priority_score`、必要时对象候选；提示由 `ai_optional_choice_score` 和 `heroes/ai_policy.py::object_owned_optional_choice` 评分 |
| 定向验收 | `tests/test_behavior.py` 中一批一类；测规则边界、玩家声明、AI 正式入口、网页预览协议，而非仅测内部函数 |

常用主路径：`registry.create_battle` 建本体 → `excel_roster` 按 kit 装配 → `Battle` 生成行动预览和声明 → 对象执行/排队效果 → 三路 AI 从同一预览造合法载荷并调用对象评分 → 网页消费同一选择协议。沿这条路径只查当前将涉及的节点；共享结构改动要记录责任对象、调用者和场景覆盖。

## 交付前的短检查

- 新模块与 kit：`python tools/check_local_import_symbols.py <hero.py> <kit.py>`。
- 定向类：`python tools/check_focused_test_symbols.py <NewBatch...BehaviorTests>`；再做 `compileall`、JS 语法检查（若改网页）、JSON 解析和 `git diff --check`。这些都是静态检查；动态测试及 AI 对局由用户运行。
- **测试夹具先核实际棋盘尺寸。** `Battle()` 默认 8×8；`registry.create_battle` 的标准棋盘由双方阵容决定。形状的名义大小不等于棋边裁切后的格数。对 11×11 等范围，断言“名义格集合 ∩ 当前棋盘”，同时在足够大的棋盘覆盖完整 121 格；不要在默认夹具上硬写 121。
- 核对预览与实际载荷、参数名与必填字段、导入符号、合法目标和落格、AI 实际入口、计数/冷却不因复出刷新。若用户专场失败，先从报告目录读完整日志，修当前批次，不开启下一批。
