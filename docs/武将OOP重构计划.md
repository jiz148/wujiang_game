# 武将 OOP 渐进重构计划

状态：公开武将的**装配层**已全部迁移：107/107 名公开 Excel 武将使用 `HeroKit`，其余18名公开武将原本由独立英雄类装配，共125/125。旧中心专属装配工厂已删除；专属机制类、AI、目标选择和共享引擎的 OOP 整理仍未完成。完整回归红基线尚未关闭。适用阶段：Phase H1 的武将开发基础重构。目标是让普通新武将的规则、AI 和目标选择尽量由本武将模块及通用能力承载，减少修改和阅读大型中心文件的次数。**每个原子重构批次必须实际运行足够的测试，通过后才能继续下一批。**

2026-10-24 新增强制开发规则：以后**所有**武将战场相关开发都必须遵守 OOP，不只限于本轮重构。新需求不能继续向中心工厂、引擎、AI 或前端加入按武将/技能编号增长的行为分支；缺少扩展点时先补对象接口。规则详见项目 skill 与《架构分层说明》。

## 加速交付顺序

优先满足“以后开发一个武将不再反复修改和阅读多个中心大文件”这个核心目标。**不以迁完全部历史武将作为新 OOP 开发路径上线的前置条件**；旧武将保留兼容入口并逐批迁移，新开发立即走对象入口。测试门槛不因加速降低。

| 交付点 | 目标用时（单人持续开发，非承诺） | 可验收结果 |
|---|---|---|
| 基线及首个可用 OOP 路径 | 约 3–7 个工作日；当前基线失败可能延长 | `HeroKit`/注册与 AI 策略入口、一个普通和一个复杂样本迁移通过测试；新的常规武将不再增加中心编号分支。 |
| 中心热点瘦身 | 再约 1–3 周 | 通过重复机制的成组迁移，把工厂、AI 载荷/评分和常见选择模式的高频分支搬到对象接口；每批实际跑门槛测试。 |
| 全部历史公开武将及引擎旧分支清理 | 另需数周；首批实测后重新估算 | 清掉旧兼容路径和剩余历史分支，完成全公开武将审计。此项不阻挡前两个交付点投入后续武将开发。 |

提速手段是利用现有 `Skill`/`Trait` 类，先接对象装配和分发，再迁移已存在的实现；机械性注册/移动可用脚本辅助，规则和 AI 决策仍逐批人工核对。单个批次最多覆盖少量同机制武将，完成定向与完整测试后才扩下一批。前两个交付点的实际耗时将在基线修复和首批迁移后按数据校准。

## 现状与目标

现有 `AbstractHero`、`Skill`、`Trait`、`StatusEffect` 已是对象模型，战斗规则也通过组件钩子运行。主要成本来自对象**装配和决策的位置**：

- `heroes/excel_roster.py` 约 1.7 万行，特殊技能与特性工厂按武将编号和中文片段匹配；当前可检索到约 310 处武将编号条件。
- `rooms/ai.py` 约 1 万行，技能候选、载荷生成、评分及反应评分集中在同一模块；按编号或技能代码判断的条件约 469 处。简单 AI 与倾向 AI 还有独立路径。
- `engine/core.py` 约 8 千行，既有通用动作/连锁生命周期，也有逐渐积累的特殊机制。前端 `targeting.js`、`vfx.js` 仍有少量按技能代码特判。
- `excel_roster_data.py` 是生成的源数据，不能通过移动它来衡量架构改善。

最终的常规开发路径：源规则和设计基线 → 一个武将模块定义技能、特性和专属 AI 策略 → 注册 → 场景测试。已有通用目标选择模式由后端预览元数据驱动前端。只有产生**新的通用机制**时才修改引擎、通用 AI 或前端选择器。

## 设计边界

1. 保留现有 `Battle`、`Unit`、`Skill`、`Trait` 的公开行为和 JSON 协议；采用组合与小接口，不建立多层武将继承树。
2. 一个武将的技能、特性和专属 AI 决策由同一个武将模块拥有。可复用机制留在 `heroes/common.py` 或按机制拆出的通用模块，不能复制到多个武将类。
3. `HeroDefinition` 只描述身份、组件工厂和可选能力扩展；战斗中的次数、冷却、状态保存在每次创建的 `Skill`、`Trait`、`Unit` 实例里，注册表不得共享可变运行状态。
4. 引擎只调用能力接口，不导入具体武将类。AI 的通用候选/估伤仍留在 AI 层，专属策略只接管专属载荷或增量评分；不得让战斗规则依赖 AI。
5. 原始 Excel 文本和设计档案继续是规则依据。未知或含额外文字的片段必须显式处理，不能因工厂迁移而自动解释成通用技能。
6. 保留现有战场快照、回放、连锁顺序、随机数和 ID 消耗语义。当前 direct AI 的源码/对象身份守卫、生成契约及缓存需要随代码迁移核对，不能只比较最终选招。

建议的最小接口形状（名称可在首批迁移时按实际依赖微调）：

```python
@dataclass(frozen=True)
class HeroDefinition:
    code: str
    kit: HeroKit
    ai_policy: HeroAIPolicy | None = None

class HeroKit:
    def create_skills(self, source_spec) -> list[Skill]: ...
    def create_traits(self, source_spec) -> list[Trait]: ...

class HeroAIPolicy:
    def payloads(self, context, action) -> list[dict] | None: ...
    def score_delta(self, context, action, payload) -> float | None: ...
```

`None` 表示交还通用实现；策略注册表在 AI 层查询 `HeroDefinition`，不把 AI 实例绑到战斗单位。该接口只定义扩展点，不要求每名武将都写空方法。

## 分步实施

### 0. 固定现状和迁移门槛

- 记录现有公开武将注册、源片段到组件的映射、`Skill`/`Trait` 生命周期、AI 三条路径及前端 `selection.mode` 清单；把新旧实现的责任边界写入架构文档。
- 选一个已验收的普通武将和一个含专属 AI/复杂选择的已验收武将作样本。先从锁定的设计基线推导行为，再看实现；不以旧代码作为规则定义。
- 对样本保存确定性行为断言：可用动作与预览、载荷、实际结算、连锁/回合边界、公开状态，以及 AI 候选、评分、选择、状态/RNG/ID。此阶段不改规则。
- 量化基线：开发一个样本武将需要修改的运行时代码文件数、中心文件新增分支数、需读的代码范围。以后每步对照这三项。

**完成标准**：能在同一固定输入上判断迁移是否改变规则、AI 决策或副作用；当前工作区未提交改动有清楚边界。

### 1. 建立武将装配对象，保留旧入口

- 新增小型 `HeroDefinition` / `HeroKit` 接口和显式注册表：`create_skills()`、`create_traits()`，必要时提供单位能力扩展和 AI 策略。`registry.create_hero()` 及公开名册继续使用原有 code。
- Excel 生成的身份/属性数据继续交给现有类工厂；仅把“这个武将装哪些组件”改为优先查询 kit，未迁移武将走旧工厂。禁止在新注册表中重新维护一份基础数值。
- 先迁移一个普通样本，确认技能实例逐次创建、组件绑定和公开状态与旧入口一致。

**完成标准**：旧武将零行为变化；新入口能独立装配一个武将；以后新增武将不需要再给 `_special_skill_factory` / `_special_trait_factory` 加分支。

### 2. 按武将把规则迁出大工厂

- 每批迁移少量互不强耦合的已实现武将，把相关技能、特性、召唤物和 kit 放在该武将模块；共享效果只抽一次为通用组件。关联武将可共用一个机制模块，但注册与设计基线仍逐人明确。
- 删除已迁移编号在旧工厂和 `_make_build_skills` / `_make_build_traits` 的分支，禁止新旧两套装配同时生效。对额外技能、临时获技、克隆、坐骑和多格入场设置明确能力钩子，不靠对生成类动态塞方法。
- 将中文片段匹配限制在源数据适配层；对专属组件使用明确的武将 code/片段契约并检查源文本漂移。

**完成标准**：每迁移一人，原大工厂相关分支确实减少，实例行为和公开 JSON 保持一致；新模块不复制通用规则。

### 3. 将专属 AI 变成策略对象

- 定义轻量 `HeroAIPolicy` 接口，仅提供有专属规则时才需要的 `payloads`、`score_delta`、`reaction` 等能力。通用 AI 仍统一负责合法性、基准评分、候选排序和资源约束。
- `ai.py` 先加“注册策略优先、旧分支兜底”的适配层；逐人迁移评分/载荷并随即删除旧分支。简单 AI 和倾向 AI 尽量消费同一策略的决策提示，保留各自难度权重。
- 每批以固定输入比较**全部候选及分数**、最终动作、战场状态、RNG 和 ID。direct/legacy 两条路径分别检查；源码指纹、原生构建契约和缓存守卫要跟随迁移更新。实际运行本批武将 AI 对局及适用的全公开池审计，结果记入该批报告。

**完成标准**：迁移武将无需再改 `rooms/ai.py` 的技能编号长链；短时性能无明确退化，优化路径实际命中，legacy 仍可手动启用。

### 4. 统一目标选择契约

- 将现有 `preview.selection.mode` 中已能表达的选择，整理为按选择模式工作的载荷构造器。后端合法选项/预览是唯一来源；AI 和前端分别用同一选择模式解释它，不再各自按技能名猜格式。
- 先覆盖常见的单位、格子、区域、方向、路径和多阶段选择；独特机制可注册专属模式，但必须同时给后端合法性、前端点击/高亮和 AI 候选提供同一契约。
- 迁移一个现有复杂选择样本后，清掉相应 `targeting.js` / `vfx.js` 技能代码特判。

**完成标准**：常规新技能只提供预览/选择元数据，不在前端增加技能编号分支；真人选择与 AI 载荷均能通过后端验证。

### 5. 收敛引擎中的特殊规则

- 等武将组件和选择契约稳定后，再逐块把 `Battle` 中的特殊规则改为清晰的扩展点：动作声明、付款、连锁窗口、结算、伤害/状态生命周期和公开状态。每次只抽一个完整生命周期，保持调用顺序可见。
- 通用结算留在引擎；仅与某武将有关的判定移到其 `Skill` / `Trait` / 能力对象。现有钩子能表达时直接复用，不额外发明事件总线。
- 最后按职责拆 `core.py`，避免纯粹把行数搬到多个文件而保留同样的跨层依赖。

**完成标准**：新增英雄特殊规则主要由组件实现；引擎新扩展点有明确调用时机、输入、可改变的结果及场景覆盖。

### 6. 清理与新武将模板

- 迁完已选样本及后续批次，删除失效的编号分支、旧工厂兜底和重复辅助函数；未迁移旧武将仍可继续运行，直到覆盖范围明确扩大后再移除兼容层。
- 在开发文档加入一个极简新武将示例和检查清单，列出设计基线、组件、AI、前端预览、测试各自应放的位置。
- 用真实下一名新武将检验：常规机制应只新增武将模块、注册与测试/设计材料；记录修改文件数、中心分支数和准备上下文范围，与第 0 步基线比较。

**完成标准**：新开发路径实际减少跨文件修改和阅读量；没有靠隐藏分支或降低测试覆盖来达成指标。

## 实施顺序与风险控制

- 顺序固定为 **装配 → 武将规则 → 专属 AI → 目标选择 → 引擎**。先迁已验收且机制较稳定的样本；近期尚待动态专场的 R328/R329、R373 暂不作首批样本。
- 每批只做一种架构迁移，保留旧入口给未迁移武将。每次删除旧分支与接入新对象在同一批完成，避免双重触发。
- 不在架构重构中顺手改规则或 AI 权重；发现既有规则错误，单独记录、按锁定设计处理，并与纯迁移结果分开验证。
- 目前工作区有大量未提交改动。实施时逐文件确认现有差异，以小补丁落地，不重置或覆盖这些改动。
- 按项目规则同步更新 `references/project-map.md`；如果改变玩家可见行为，再同步规则文档与行为测试。新英雄仍遵守设计先锁、静态候选门禁和当前 Phase H1 顺序。

## 每一步的测试门槛

这里的“一步”指一个可独立回退的代码改动或一个小批次武将迁移，不是上面七个大阶段全部完成以后才测。先测再迁移；测试不通过就停在当前步，查明是新回归还是已有基线问题，修复并重跑，不带着未解释的失败进入下一步。

| 改动范围 | 每步必须实际运行的检查 |
|---|---|
| 所有代码迁移 | 涉及模块的导入/语法检查；对应武将或机制的确定性 `tests/test_battle.py`、`tests/test_behavior.py` 等定向用例；从仓库根目录并确保 `src` 在 `PYTHONPATH` 后运行 `python -m unittest discover -s tests` 完整回归。记录通过、失败、跳过和耗时，与迁移前基线比较。 |
| 武将装配、技能、特性 | 核对组件类型/数量/绑定、每实例独立状态、行动/预览、付费/次数/冷却、连锁/回合边界、公开 JSON；运行本武将定向审计 `python detail_test_all_wujiangs.py --targets <codes> --out <本批目录>`，检查代表性真人规则场景和 AI 对局轨迹。 |
| 专属或通用 AI | 固定种子比较迁移前后全部合法候选、载荷、评分和选择，同时比较战场状态、RNG、ID；测试标准、简单、倾向三条路径及 direct/legacy。运行受影响武将审计；改到共享评分/候选入口时，再运行无 `--targets` 的全公开武将审计。 |
| 后端预览或前端选择 | 运行目标合法性、预览、点击与提交载荷的行为测试；实际运行 `node tools/verify_frontend_modules.mjs`、`python tools/verify_frontend_globals.py`、`python tools/verify_frontend_dom_ids.py`、`python tools/verify_frontend_boot.py`。浏览器缺失导致跳过时明确记录，不能把跳过当通过。 |
| 引擎公共生命周期或注册分发 | 在定向边界与完整 unittest 外，运行无 `--targets` 的全公开武将审计；覆盖连锁、死亡/召唤、状态到期、随机效果、多人/自走棋等受影响路径。 |

第 0 步先跑一遍完整 unittest 和前端检查，保存当前失败/跳过基线；先修复阻塞性的测试环境与工具错误，并将剩余基线失败逐项归因。若之后的测试新增失败，必须先修复或证明与本批无关并记录证据。每批报告包含修改范围、测试命令、退出码、关键结果、前后对照和残留限制。纯文档调整不算代码重构，无须重复全套动态测试。

当前未提交工作区的全量 unittest 在 AI 控制诊断中超出短时预算，`test_battle.py` 有与当前出手顺序及公开名册不符的既有红项。在这项基线修复前，**仅装配层的武将迁移**可采用可复核的红基线门槛：可成组改动，但每名武将迁移前均须保存公开状态及动作快照和固定种子对局轨迹，迁移后逐字节比较；组件与相关行为测试必须全过；定向动态审计必须完成且无新增高信号；再运行宽范围战斗 smoke 与旧红项对照。任何本将新增失败或轨迹差异立即停止。完整套件必须继续列为未通过；此例外不适用于共享引擎、AI 或前端行为改动，基线可运行后恢复完整门槛。
