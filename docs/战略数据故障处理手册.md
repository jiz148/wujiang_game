# 战略数据故障处理手册

本手册用于 Phase 7 P7.4.4 的生产数据事故。目标是保留现场、限制修复范围、保证每次写入都有计划、确认、执行前快照、审计记录和执行后诊断。工具不提供任意 SQL。

## 一、硬性原则

1. 先停止对外服务，再执行任何 `apply`。维护标记只能阻止新的 `StrategyStore` 连接，不能替代停止整个服务进程，也不能阻止其他程序直接写共享 SQLite。
2. 先运行只读诊断和备份演练；不要先修改数据库来“看看是否有效”。
3. 修复计划生成后，只要数据库发生任何变化，旧计划自动失效，必须重新生成。
4. 执行必须具备可追溯运维账号、固定原因码、计划 ID 精确确认，以及至少 16 字符的独立管理密钥。
5. 不删除或重算审计历史，不用新摘要掩盖损坏，不从无法验证的备份恢复。
6. 不手工删除 `.maintenance.json`，除非已确认没有修复进程和游戏服务仍在运行，并保存该标记内容到事故记录。

## 二、准备与只读诊断

停止服务后设置数据库和备份目录，并运行：

```powershell
python tools/strategy_diagnostics.py --db <数据库> --backup-dir <备份目录> check
python tools/strategy_backup.py --db <数据库> --backup-dir <备份目录> list
```

保存完整 JSON 输出。`critical` 表示不能继续正常写入；`warning` 需要人工判断，但不会自动触发修复。

## 三、白名单索引修复

当前唯一的原位修复是：当 `world_json` 能完整反序列化时，以它为权威同步 `strategy_campaigns.current_month`，以及把世界已经归档但索引尚未归档的战役同步为 `archived`。工具不会反向猜测世界内容，不修改军令载荷、战斗快照、成员、资源或审计历史。

生成计划：

```powershell
python tools/strategy_repair.py --db <数据库> --backup-dir <备份目录> plan --out repair-plan.json
```

检查 `actions` 和 `blocked_findings`。存在任何 `blocked_findings` 时禁止执行。执行前在服务环境配置：

```powershell
$env:WUJIANG_STRATEGY_REPAIR_TOKEN='<独立管理密钥>'
$env:WUJIANG_STRATEGY_REPAIR_APPROVAL='<本次输入的相同密钥>'
```

双人复核计划 ID 后执行：

```powershell
python tools/strategy_repair.py --db <数据库> --backup-dir <备份目录> apply repair-plan.json --confirm <plan_id> --operator <运维账号> --reason-code <事故号或变更号>
```

执行会建立维护标记、创建 `pre_repair-*` 快照、重新核对目标、只执行白名单字段更新、追加防篡改管理审计、验证审计链并运行完整诊断。任一步失败都会中止；已进入事务的修改会回滚。

## 四、从已验证整库备份恢复

适用于审计链损坏、世界载荷无法读取、结构损坏或其他不能原位修复的问题。候选备份必须在受管目录中，清单/大小/SHA-256/SQLite 校验通过，隔离恢复演练通过，并与当前服务的数据库结构版本和世界存档版本完全一致。

先验证和演练：

```powershell
python tools/strategy_backup.py --db <数据库> --backup-dir <备份目录> verify <备份文件>
python tools/strategy_backup.py --db <数据库> --backup-dir <备份目录> drill <备份文件>
```

生成恢复计划：

```powershell
python tools/strategy_repair.py --db <数据库> --backup-dir <备份目录> restore-plan <备份文件> --out restore-plan.json
```

确认备份时间、版本、摘要和可接受的数据回退窗口。然后使用与上一节相同的受限 `apply` 命令执行。工具会先保存当前在线库的 `pre_restore-*` 快照，再把候选备份复制到同目录临时库，追加恢复审计、完成全诊断后才原子替换数据库文件。恢复失败时保留执行前快照，不静默尝试第二个备份。

## 五、不能自动修复的故障

以下情况必须停止并升级，或选择已验证整库恢复：

- 审计链被改写、断裂或无法解析。
- 世界 JSON 无法解析、存档版本来自未来或缺少已登记迁移路径。
- 战斗检查点摘要、参与者或战役/房间绑定不一致。玩家仍可使用既有“从不可变战前快照安全重开”，管理工具不会伪造检查点。
- 外键损坏、结构迁移账本缺失/出现未来版本、SQLite 完整性检查失败。
- 数据库已损坏到无法创建执行前一致快照。
- 需要改变成员归属、资源、胜负、战役历史或玩家军令内容。

## 六、执行后验收与回退

1. 保存 `apply` 的 JSON 输出和 `pre_repair-*` / `pre_restore-*` 路径。
2. 再次运行 `strategy_diagnostics.py check` 和 `strategy_diagnostics.py audit`。
3. 启动服务后，用原成员账号验证战役列表、地图月份、归档只读状态和未完成战斗恢复。
4. 若执行后仍为 `critical`，立即停止服务，不连续尝试其他原位修复；使用执行前快照生成新的恢复计划。
5. 将运维账号、原因码、计划 ID、诊断前后输出、使用备份和玩家影响时间窗登记到事故记录。管理密钥不得写入记录、命令文件或审计详情。

## 七、遗留维护标记

标记路径为 `<数据库文件名>.maintenance.json`。若工具异常退出：

1. 确认游戏服务和所有修复进程均已停止。
2. 保存标记文件内容和文件时间。
3. 运行只读诊断，确认数据库当前状态。
4. 若计划没有提交，保留/验证执行前快照后删除标记并重新生成计划；若无法判断是否提交，按事故升级处理，不直接恢复服务。
