# 房间大厅与对战记录改造

这份文档是这一轮的总控。先记清现状和决定，再按依赖改，避免一边改界面一边把战场、录像和房间状态机搅在一起。

## 现状（2026-10）

**战场引擎已经接近「配置进、对战出」。** `tactical/engine/core.py` 的 `Battle` 不认识房间模式。真正的上帝对象是 `tactical/rooms/multiplayer.py` 的 `GameRoom`：标准选将、随机、BP、自走棋、战役回放都长在它身上。战役通过 `bridge/battle_bridge.py` 在开局前把攻城单位写进同一个 `Battle`。这一轮不拆 `GameRoom`（拆开会同时撞上录像和房间 API），只保证新功能不再往引擎里塞模式分支。自走棋超时仍有一处 `engine` → `autochess` 的 import，留到下一刀：改成开局配置里的回调。

**创建房间不选模式。** `POST /api/rooms/create` 能收 `mode`，界面没传，默认 `classic`，进房后再用设置弹窗改。主菜单叫「遭遇战」，页头再写一遍「建立房间 / 加入房间」和两段说明。

**房间列表没有过期。** 房间本体在进程内存（`RoomRegistry._rooms`），不是账号数据库。自走棋额外把整房 pickle 到 `var/autochess/*.room`，列表接口会把磁盘上的旧房重新装回内存。已结束的房间也一直留在公开列表里。落盘策略这一轮只做「已结束的不再展示，磁盘上已结束的自走棋检查点不再装回来」，不设计新的持久化。

**BP 的规则是齐的，界面不是。** 后端 `bp_choose` 已经按步骤校验禁/选。前端是「等级下拉 + 武将下拉 + 确认」，阶段和结果都是一行小字。

**录像是全量快照，不是动作日志。** 每步 `ReplayRecorder.append_step` 存三份完整战场公开状态（全知、观战、每个席位）。终局一次写成 `replays/*.json`。战绩库只存路径。自走棋的子战斗没有打开降采样，每一步 AI 都做这三份序列化，而且发生在 `GET /api/rooms/state` 持有的房间锁里，每次轮询只推进 2 步。卡顿的主因是这条链路：请求线程里的 AI 搜索，乘上每步的全量序列化。写盘发生在终局，不是每步，但是内存和 CPU 每步都在付。没有全局开关。

## 这一轮做的

1. **记录三档**，存在 `var/app-settings.json`，接口 `GET/POST /api/settings`（需登录）。
   - `full`：维持现在的逐步全量快照，默认值，已有回放和测试不变。
   - `actions`：只在开局存一份全量状态，之后每步只记原因、回合和胜负，不再复制整张棋盘。战绩仍入库，但回放按钮关闭（逐步回放要能重演才有意义，这一轮不做重演器）。
   - `off`：不写 `replays/`。有真人参与的对局仍写入战绩（胜负、时长、席位），回放入口保持关闭。
2. **自走棋子战斗一律不录像**，并打开已有的 `fast_ai_simulation`（只跳过视觉事件和逐步快照，不改判胜）。这和全局开关无关：那些子局本来就不是给人回放的，却是卡顿的主要来源。
3. **主菜单「遭遇战」改为「房间大厅」。** 进去就是房间列表。创建先选模式（战场对战 / BP / 自走棋），再进对应房间。加入收成房间码一个输入框。列表用标签表示模式、人数、状态，已结束的房间不出现在列表里。
4. **BP 改为武将矩阵。** 阶段用大字「禁用 / 选取」而不是一句说明；两边分列已经禁用和已经选取的人；矩阵里点合法武将即提交，点谁都能看资料。BP 房间不再配置士兵。
5. **按钮增加请求中状态**（`.is-busy`），创建房间会用到。

## 明确不做（下一轮）

- 把 `GameRoom` 拆成「模式状态机产出开局配置，战场只吃配置」。契约目标是一份 `BattleSetup`（名单、棋盘、挡格、回合上限），BP / 自走棋 / 战役都只负责把这份配置填满。
- 动作记录的重演回放。现在 `actions` 档的文件已经按「开局 + 动作」落下，播放器还在等重演。
- 自走棋战斗改到请求线程之外。如果关掉录像之后战斗阶段仍然卡住，下一步是把 AI 步挪出 `GET /api/rooms/state`，而不是再加大每次轮询的步数（那只会让单次请求更久）。
- 房间的长期存储。现在除了自走棋检查点，房间不落数据库。
