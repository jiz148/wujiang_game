# 架构分层说明

这份文档描述项目**当前**的代码组织方式。目标只有一个：让你在开发某一方面功能时，只需要打开与之相关的目录，不必在无关代码里穿行。

`docs/产品开发路线图.md` 和项目地图里的历史阶段记录使用的是重构前的路径（如 `web/server.py`、`strategy/store.py`、`static/app.js`）。那些记录描述的是当时的事实，**保持原样不做改写**；下面的对照表说明它们对应到今天的哪个位置。

## 四个域

代码按**领域**分包，而不是按技术分层：

| 目录 | 职责 | 能依赖谁 |
|---|---|---|
| `src/wujiang/platform/` | 与玩法无关的平台能力：HTTP 内核、账号、分析、战绩、限流、可观测性、部署校验 | 谁也不依赖（不得引用 tactical / strategic） |
| `src/wujiang/tactical/` | 战术域：格子战斗引擎、武将、战斗房间 | platform、bridge |
| `src/wujiang/strategic/` | 战略域：战役世界、城市、军队、外交、遗物、危机 | platform、bridge |
| `src/wujiang/bridge/` | 两个游戏域之间的唯一通道 | tactical、strategic、platform |

**核心约束：`tactical/` 与 `strategic/` 不得互相导入。** 一切跨域调用都必须经过 `bridge/`。

前端用同样的结构镜像这套划分：

```
static/
├── app.js                      入口，只负责启动
├── core/     state / net / ui / render / events
├── platform/ auth / home
├── tactical/ session / vfx / targeting / battle-ui / room-api / board-input
├── strategic/ api / ui-base / workbench
└── bridge/   campaign-battle.js
```

## 桥接契约

两个域之间的全部交互都收敛在两个文件里，想知道"战略和战术之间到底发生了什么"，读这两个文件就够了：

- **后端 `src/wujiang/bridge/battle_bridge.py`**：把战役冲突翻译成格子战房间（出兵名单、防守方、快照），再把战斗结果写回战役（存活比例、士气、占领、英雄沉睡）。
- **前端 `static/bridge/campaign-battle.js`**：战役界面调用战场能力（应用房间数据、读写席位身份、行动名称）与战场回写战役状态的完整清单，共 10 个符号。

新增跨域调用时，加在桥里，不要在两个域之间直连。这条约束由 `tests/test_frontend_modules.py` 自动检查。

## HTTP 路由的组织方式

不再有集中的路由长链。每个域用装饰器登记自己的接口：

```python
from wujiang.platform.http.routing import post

@post("/api/rooms/create")
def post_rooms_create(ctx: RequestContext) -> None:
    ...
```

`platform/http/handler.py`（内核）只负责传输安全、限流、鉴权与分发，不认识任何具体接口。
`platform/http/server.py`（组合根）通过导入三个域的 `api` 模块完成装配——**新增一个域只需在这里加一行**。

当前分布：平台 11 个路由、战术 34 个、战略 31 个。

就绪探针同理，各域自己注册依赖：

```python
register_dependency("strategy", lambda: STRATEGY_STORE)
```

## 前后端的关系

前端是纯静态 SPA，只通过 JSON API 与后端交互，**没有任何服务端模板渲染**。所以前后端在运行时层面已经是分离的；Python 进程同时托管 `static/` 只是部署上的便利，不构成代码耦合。

因此本项目**不做**独立部署式的前后端分离：那会引入 CORS、双服务启动和构建产物，而收益为零。

前端使用**原生 ES Modules，无构建步骤、无 npm 依赖**。根目录的 `package.json` 只用于向 Node 工具声明 `static/` 是 ES 模块，不是一个 npm 工程。

`static/` 里有三个文件仍是经典脚本而非模块：`platform/home-ui.js`、`tactical/replay-ui.js`、`tactical/battle-feedback.js`。它们通过 `globalThis.Wujiang*` 命名空间暴露，被 quickjs 行为测试直接求值。它们已经是独立模块，转换成 ESM 只会增加测试改造成本而无结构收益。

## 屏幕路由

在此之前整个应用只有 `draft` 和 `battle` 两屏，而首页、登录、战役、房间大厅、武将库全部堆在 `draft` 内部靠 `.hidden` 互相遮挡。最能说明问题的是战情室那三个"标签页"：`focusStrategyCommandPanel` 之类的函数只是 `scrollIntoView`，什么也不切换——内容始终全部存在，只是让玩家滚过去。于是"什么时候该显示什么"在代码里根本无从表达。

现在 `core/router.js` 把屏幕提升为一等概念：`gate`、`menu`、`draft`、`battle`，同一时刻只有一个存在于视口内，DOM 中对应 `#<name>-screen`。`body` 上会带 `screen-<name>`，样式据此收敛外壳——登录门与主菜单不显示顶栏。

由此带来的一条纪律：**页头归当前流程所有**。此前 `renderRoomPanels()` 在"没有房间"时无条件把页头写成房间大厅的文案，而它在 `renderHomeFlow()` 之后执行，结果玩家明明在战役里，页头却始终写着"在线房间"。现在房间模块只在真的进了房间之后才接管页头。任何模块要写共享区域前，都应当先确认自己是不是当前屏幕的主人。

登录做成了硬门禁。后端对所有开局接口一律要求账号（无令牌一律 401），前端此前却让玩家先浏览、点下去才撞 401，登录表单还藏在首页 DOM 底部、且只有选了模式才出现。现在未登录时 `render()` 直接短路到登录门，不渲染任何主内容。

主菜单刻意不区分单人与多人：一局对局天然带槽位，AI 只是默认占位者，真人可以顶替、中途加入或纯观战。"有没有真人"属于对局内部状态，不是菜单上的选择。

菜单里战役与遭遇战并列，而不是后者作为前者的简化档。两者的区别是要不要经营大地图：战役有城市、科技、月份推进；遭遇战直接摆开一场战斗。遭遇战同样能建房、发邀请码、让真人顶替 AI 席位——多人与否两边都不构成区分维度。它的三个入口（立即对 AI 开战 / 建房选将 / 房间码加入）此前散落在两个互不相干的流程里，一半在"快速开始"、一半在"自定义对战"，玩家很难看出它们通向同一件事。

**地址栏写的是去处，不是容器。** `draft` 屏同时承载战役、遭遇战、教学、档案四个流程，因此 `#draft` 这个地址什么也没说明——重新打开时无从知道该还原成哪一个。而旧的 `screenHash()` 恰恰把除战斗外的一切都写成 `#draft`，包括主菜单：于是玩家在菜单上停留时，地址栏已经悄悄变成了 `#draft`，下次打开读到它就直接跳进内层，只能靠点「主菜单」退回来。现在 `screenRoute()` / `routeTarget()` 用流程名作地址（`#campaign` / `#skirmish` / `#tutorial` / `#archive`），流程名与代码里的 `state.homeFlow` 取值是同一套词汇，无法识别的地址一律回主菜单而不是掉进某个内层。

同样的"一件事写两遍"曾出现在文案上：`hydrateStaticLabels()` 在启动时把二十来个按钮和段落的文字重写一遍，而每一条 `index.html` 里都已经写过。代价是改文案要改两处，且 JS 那份总会覆盖标记——新加的按钮文案会莫名其妙地被改回旧词。文案现在归标记所有。

**该显示哪一屏要等接口回来才知道，所以启动时先谁都不显示。** 标记里必须有一屏是默认可见的，而它未必是登录后该落到的那一屏——于是打开页面会先闪一下房间大厅，再跳到主菜单。`body.is-booting` 让外壳在 `/api/auth/me` 回来之前保持 `visibility: hidden`，`applyScreen()` 定下归属后摘掉。启动失败的分支也要摘，否则报错横幅会连同外壳一起被藏起来，只剩一片空白。

**房间是被"看着"的东西，不是玩家的常驻身份。** 房间大厅是否显示只看手上有没有房间，不看玩家在哪个流程里；只要地址栏还挂着 `?room=`，从主菜单点战役也会被房间大厅盖掉，看上去就像点战役跳进了遭遇战。现在从主菜单选去处会调用 `leaveRoomView()` 把房间摘出视图——服务端的房间和本地存的席位身份都还在，遭遇战屏的房间列表（`#room-directory`，此前因流程改名而成了永不显示的孤儿）和邀请链接都能回去。

## 设计系统

`static/theme.css` 是全站视觉的单一事实来源，必须在 `styles.css` 之前加载，包含设计令牌、基础重置与组件层（`.btn` / `.input` / `.field` / `.panel` / `.card` / `.tabs` / `.chip` / `.hint`）。按钮的变体与尺寸正交：变体决定语义，尺寸决定高度，需要换色时覆盖 `--btn-accent`，不要再写一套背景色。

改造前 `styles.css` 有 6384 行，其中真正可复用的基础层只有约 200 行（3%），其余全是特性专用样式；颜色字面量有 620 种、85% 只出现一次；圆角有 23 种取值，落在 4–8px 的仅 16%，主流是 16–28px；仅按钮就有 8 套并行实现。而且整体是浅色羊皮纸主题，中间又嵌着几块深色孤岛（战情室、Analytics、模式入口），本身就是分裂的。

因此没有逐条重写那 6384 行，而是走了两条杠杆：其一，`theme.css` 末尾把 `--panel` / `--ink` 这些旧令牌重新指向新的暗色令牌，历史样式整体翻暗——原有的深色孤岛反而因此变得协调；其二，`button` / `input` / `.panel` 都是全局选择器，把它们对齐到组件层，全站现有控件无需改动标记就拿到了新的尺寸、圆角与交互反馈。圆角另有一次脚本化收敛，把 113 处取值映射到 `--r-1/2/3` 三档。

杠杆够不到的是写死的颜色字面量——它们不引用任何令牌，因此不会跟着翻暗。棋盘尤其明显：`.board-stage` 与 `.cell` 用的是一套自己的羊皮纸色，在暗色外壳里就是一块刺眼的白板。这些已归入 `--board-surface` / `--board-cell` / `--board-line`；战场比外壳略亮，让视线落在棋盘上，但仍属暗色一侧。另有 20 处面板、卡片、日志行的奶白填充改为表面令牌，10 处随之会变成"黑底黑字"的深色文字改为文字令牌。刻意保留了两处浅底深字：色盲模式的标记点，以及彩色警示条上的选中项，它们本就是深字压浅底。

`--muted` 与 `--font-display` 此前被 `var()` 引用却从未定义过，现已补上。

渐变底色也一并清掉了。原先有近三十块面板走的是同一个套路：暗底渐变 + 金色描边 + 米色文字，各自都想显得特别，凑在一起反而看不出哪块重要。它们现在统一落在表面令牌上，需要强调的改用一条左侧色条。保留渐变的只有真正的游戏表面与信号——棋子、法力点、战场特效、色盲模式的斜纹填充，以及大地图的网格与地形着色。

嵌套边框同理。`#room-home` 的直接子节点是同一块面板里的分区，外层 `.draft.panel` 已经提供了"面板感"，内层再各套一个框只会让人数不清有几层。现在它们统一被抹平，靠间距与横线分区。写成 `#room-home > *` 而非类选择器，是因为各面板自带的边框声明写在 `styles.css` 更靠后的位置，同等特异度下会赢。

另一类重复是标题：战役、战绩两屏都在页头之外又写了一遍自己的标题和说明。既然同一时刻只有一个流程可见，页头就应当归它所有——战役因此直接把当前战役名与月份写进 `#lobby-caption`，那比一句通用介绍有用得多。散落的说明段落改成了 `.hint` 悬浮提示。

`core/components.js` 是配套的 JS 组件工厂。界面几乎全部是命令式拼 DOM，只有 CSS 类推不动统一——每个新面板还是会各写各的 `createElement`。注意 `createField` 通过 `field.fieldControl` 交出控件，而不是 `field.control`：后者是 `<label>` 的只读原生属性，赋值会抛错，读取又依赖 `for` 指向的 ID 能在文档里查到，而构建时这棵树尚未挂载。

### 下拉菜单与主次

并排摆开的按钮说不出主次。顶栏右上角曾是六个同款按钮——主菜单、房间大厅、返回战场、复制邀请链接、昵称、修改昵称——其中"回到你正在打的那一局"和"退出登录"长得一模一样，而多数时刻大半个按钮条是隐藏的空位。房间头部同理，七个按钮里"开始对局"和"删除房间"并肩而立。

`createMenu()` 因此不只是省地方：把次要操作收进下拉，是为了让留在外面的那个有分量。顶栏现在只有两样——当前上下文里唯一要紧的动作（`core/topbar.js` 的 `primaryAction()`），以及一个以昵称为标签的账号菜单。顶栏由 `core/topbar.js` 独占，此前它归 `tactical/battle-ui.js` 的 `renderNavigation()` 管，是战术域在写全站共享外壳。

`createMenu({ children })` 可以收纳已经存在的按钮：它们的 ID、监听、`.hidden` 开关全部保持原样，只是换了个容身之处，调用方不必为了搬进下拉而重写一套渲染逻辑。房间头部就是这么做的。代价是要额外判断"收进去的按钮全隐藏时触发按钮也该消失"（`.menu.is-empty`）。

有两个坑值得记下。其一，浮层用 `hidden` 属性收起，但 `[hidden]` 的 `display: none` 来自浏览器默认样式，作者样式表里的 `display: flex` 权重更高会把它盖掉——不补 `.menu__list[hidden] { display: none }`，浮层就永远是展开的，而且看起来像是渲染逻辑出了问题。其二，收进下拉的按钮自带 `.ghost` / `.btn` 的边框与底色，`.menu__item` 必须写成 `.menu__list .menu__item` 才压得过。

浮层里各项的高度必须由 `.menu__list .menu__item` 说了算，不能依赖各按钮自带的内在高度：`items` 生成的是裸 `<button>`，而 `children` 收进来的按钮带着 `.btn` / `.primary` / `.ghost` 各自的 padding 与 line-height，不统一就会几条高几条矮。所以给固定 `min-height` 加 `line-height: 1`，而不是靠 padding 撑。

账号菜单只放三项：用户信息、返回主菜单、退出登录。此前还有"房间大厅"与"复制邀请链接"——前者的显示条件（battle 屏且有房间）与左边那个上下文主按钮**完全相同**，等于同一件事摆了两遍；后者在房间头部的"更多"里已经有了。账号菜单收的应该是账号相关的东西。

`openProfileModal()` 曾只置 `state.profileModalOpen = true` 而不调 `render()`，于是点"修改昵称"没有任何反应——关闭与确认那两条路径本来就各自调了 `render()`，只有打开这条漏了。

`createMenu` 的 `id` 选项不要用来命名需要 `$()` 查找的节点：`verify_frontend_dom_ids.py` 认的是 `.id = "..."` 赋值，而 `id:` 作为选项字面量到处都是（菜单项、入口定义），一旦把它们都当成已知 DOM ID，检查就形同虚设。需要被查找的节点显式赋值 `node.id`。

### 房间屏

房间码、当前身份、邀请链接原本是三张大卡，占掉大半个首屏，承载的却是三个短词；邀请链接更是把整条 URL 摊在屏幕上，而旁边就有"复制邀请链接"。现在它们是一条状态栏（`.room-overview` / `.room-fact`），完整 URL 留在视觉隐藏的 `#invite-path-label` 里供复制用。房间配置（模式、席位数、随机武将数）同样从一整张卡收成一行控件，说明进了提示气泡。

提示气泡的 `id` 要落在 `.hint__bubble` 上而不是外层 `.hint` 上——既有代码是 `note.textContent = ...` 直接写文字的，写在外层会把叹号连同结构一起抹掉。

### 确认弹窗

删房间、离开房间、投降、退出登录此前都用 `window.confirm`。原生弹窗有三个问题：它长得不像这个应用（浅色系统控件砸在暗色界面上）、措辞和按钮文案改不了（只有"确定/取消"，说不出"删除房间"）、而且它阻塞整个页面。既然要在关键处拦一道，这一道就该由我们自己画。

删除战役也走这一道。此前战役**只能归档**，而归档的仍然留在列表里——试玩几局之后列表就再也清不干净了。归档和删除是两件事：归档是"这局打完了，留着复盘"，删除是"这局不该存在"。`delete_campaign` 只删 `strategy_campaigns` 一行，子表全部带 `ON DELETE CASCADE` 且连接开了 `PRAGMA foreign_keys`，会跟着走；审计日志是例外，它按 hash 链追加且 `campaign_id` 上没有外键，删历史条目会打断链，所以留着并补一条删除记录。审计要写在删除**之前**——`_audit_operation` 会去 `strategy_members` 查操作者用户名，那张表马上就要被级联删掉。

顺带修了"离线"：它调 `mark_offline` 写一条在线状态，本身是好的，但卡片从不显示在线状态，于是无论点多少次界面都毫无变化，看起来就是个坏按钮。现在只在你确实在线时才出现这个按钮，点完它自己消失——动作有了可见的结果。

`core/dialog.js` 的 `confirmDialog()` 返回 `Promise<boolean>`，替换 `window.confirm` 时调用点几乎不用改结构。几个细节是有意为之：焦点默认落在"取消"上（危险动作不该被一次回车确认掉）、`keydown` 监听挂在**捕获阶段**（否则空格暂停、方向键选格这些全局快捷键在弹窗开着时还会生效）、关闭后焦点交还触发它的按钮（否则 Tab 会从文档开头重来）。

### 战役屏：给屏幕一个主对象

战役此前是一条从上往下的滚动列表——地图、军令、成员、行动队列、目标、英灵、圣物、战斗记录、科技、事件依次堆叠，每一块地位相同。地位相同就意味着没有主次，玩家不知道该看哪里，于是它读起来像后台管理系统而不是游戏。

游戏的做法是给屏幕一个主对象，其余东西围绕它站位。现在的主对象是地图：左边 `.campaign-rail` 是"我有谁"，右边 `.strategy-command-panel` 是"我在看什么"，底部 `.campaign-turnbar` 是"我什么时候结束这个月"。三者由 `static/strategic/campaign-shell.js` 建出，`workbench.js` 只负责把它们摆进 `.strategy-war-main` 的三栏网格。

顶上原本还叠着五层：共享页头、一行只放"战役列表"的按钮条、一行战役消息、资源条、一条几乎空着的职位切换栏——近 180px 都还没进入游戏。它们回答的是同几个问题（我在哪局、我是谁、我有什么、怎么出去），所以合并成 `.strategy-war-hud` 一行；共享页头与那两行在 `body.campaign-mode` 下由 CSS 隐藏，职位切换栏只在真有两个以上职位时才出现。

武将列不只是名单。既然可执行的动作最终要由武将技能派生，"你还有几个人没派活"就等于"你还剩几个动作"——预算被画在屏幕上，而不是写成一行"军令 3/4 可用"。本轮先把列立起来并高亮闲置者；派活本身仍走现有军令系统，等技能表落地后再接上。

**锁一屏只在战役真正开打之后。** 大厅阶段这一屏上面还叠着出身抉择、锁定横幅和锁定按钮条；锁成一屏高就意味着这些高度全从地图那一栏里扣，地图被压成一条缝。那时它本来就是张设置页，让它按正常文档流往下滚才对。所以 `campaign-mode` 的条件里带上 `status === "active"`。

代价是大厅阶段三栏没有可继承的高度，两头都会出事：下限缺了地图被压扁，上限缺了右栏几千像素的内容把整块撑开（`overflow: auto` 只在高度受限时才滚）。所以 `.strategy-war-main` 在非 `campaign-mode` 下有一个高度带（`min-height: 62vh` / `max-height: 76vh`）。**光有 max-height 还不够**：网格行轨道默认是 `auto`，会按最高那一栏的内容撑开，容器限高只是让它溢出，栏内依然不滚——必须再写 `grid-template-rows: minmax(0, 1fr)` 把行轨道钉在容器高度上。

**说明文字要能改变你的下一步，否则不该常驻。** 战役这几屏此前挂着大量文案，清掉时可以按两种形状识别：

一是**恒真的说明**。战役卡上每张都印着"邀请已锁定 · 当前账号可直接恢复"，战役屏顶上那条状态栏三行说的都是"这局已经开打了"，快速开局卡有四行文案讲"点下去会得到什么"——每种状态下都一模一样的文字不携带任何信息。二是**复述控件本身**。"点击城市选择命令目标"、"选择一个战役后会显示城市、科技和事件"、队列明明空着旁边还写"行动队列为空"。

处理办法分三档：规则与只需读一次的解释进 `createHint()` 气泡（地图图例读法、军令锁定规则、预测口径都是这一类）；逐条的事实留在原地（武将忠诚、城市收支这些每条都不同）；整节没内容时连标题一起不渲染——`renderStrategyRecoveryOverview` 此前会画出"恢复总览"标题加"可恢复 0 场 · 待安全重开 0 场 · 已完成 0 场"加"还没有需要恢复的检查点"，一整块只为了说这里什么都没有。永久禁用的按钮同理：战役列表页上没有"这个月"可推进，"推进一月"就该隐藏而不是灰在那里。

两个实现上的坑。其一，把"推进一月""刷新"从页头**搬**到推进条是行不通的：`#strategy-current` 每次渲染都 `innerHTML = ""`，搬进去的节点会在下一次渲染时被连带删掉，之后页头和推进条就都没有按钮了。推进条因此新建按钮并转发点击，禁用判断仍照抄页头那两个，只写一处。其二，锁一屏高度要让整条链都是弹性的：`.shell` 设 `height: 100vh` 之后，`#draft-screen` / `.draft` / `#room-home` / `.strategy-panel` 每一环都要 `display: flex` + `flex: 1 1 auto` + `min-height: 0`，缺一环它就按内容撑开，把顶栏顶出视口。少写 `display: flex` 尤其隐蔽——父级给了高度，子节点作为普通块级元素根本不看。

## 验证手段

```bash
python -m unittest discover -s tests     # 全量回归，须从项目根目录运行
node tools/verify_frontend_modules.mjs   # 前端模块图链接校验
python tools/verify_frontend_globals.py  # 前端未定义标识符扫描
python tools/verify_frontend_dom_ids.py  # 查找 HTML 里已不存在的元素引用
python tools/verify_frontend_boot.py     # 真实浏览器里逐屏走完入口路径
```

前端模块图校验是新增的：它真实加载整个模块图，能发现源码字符串断言无法发现的导入错误。`tests/test_frontend_modules.py` 会调用它，并额外检查两个游戏域没有互相导入、没有游离模块。Node 不可用时该项自动跳过。

未定义标识符扫描补的是模块图校验结构上看不到的那一类问题：链接校验只能证明每个 `import` 都解析得到，而一个拆分前属于模块内私有、拆分后既没导出也没导入的裸标识符**没有 import 可供解析**，链接期完全合法，只在浏览器执行到那一行时抛 ReferenceError。`app.js` 拆分后有 13 个模块这样引用 `$`，就是靠它才发现的。因此 DOM 辅助函数 `$` 现在住在 `core/dom.js`——一个不依赖任何模块的叶子节点，放进 `net.js` 或 `ui.js` 都会把它们拖进循环依赖，而 `const` 绑定在循环依赖里会踩暂时性死区。

后两项补的是静态检查看不见的地方。

`verify_frontend_dom_ids.py` 检查 `$("...")` 引用的元素是否真的存在。这类字符串没有任何工具会验证，删掉一个元素之后所有静态检查照样通过。删掉大标题块时就漏了一处：`renderHeader()` 仍在写 `#topbar-subline`，于是每一条通往战斗的路径都被 `Cannot set properties of null` 挡死，而调用方 `catch` 掉了它——玩家看到的是一个卡在"正在准备对战…"的按钮和一个干净的控制台。运行时创建的元素（`node.id = "..."`）会被自动识别，因此不需要维护白名单。

`verify_frontend_boot.py` 则覆盖运行时。前面提到的组件工厂也踩过一次：`createField` 给 `<label>` 的 `control` 赋值，那是只读属性，严格模式下直接抛 `TypeError`。它用 DevTools 协议驱动浏览器，沿入口路径逐屏断言：登录门 → 主菜单 → 战役列表 → 战役开局 → 遭遇战 → 战场。**必须一路走到底**，因为每一屏都只能经由上一屏抵达，而上面那个 bug 恰好是前三屏全部放过、只在第四屏爆炸的。

"战役开局"是后补的一步，教训同源：战役**列表**和真正的战役屏几乎没有共同代码。给 SVG 的 `className` 赋值（那是只读的 `SVGAnimatedString`）让地图渲染整个崩掉，而列表照常显示，于是每一项检查都放行，点下去只得到一屏空白。这一步还顺带断言战役屏没有撑破视口——地图是主对象，页面一旦滚起来顶栏就被推走。

它同时断言地址栏写的是去处：主菜单不得留下内层容器名，各流程的地址要能直达该流程。

之所以不用 `--dump-dom` 或 `--screenshot` 这类快照参数，是因为本应用要先 `await` `/api/auth/me` 和 `/api/heroes` 才能决定显示哪一屏，而快照发生在那之前，无论把 `--virtual-time-budget` 调到多大都只会拍到登录门——虚拟时间不会等待真实网络请求。协议方式可以等待真实条件而不是猜一个时长。项目坚持不引入 npm 依赖和构建步骤，所以 `tools/cdp.py` 用标准库直接实现了协议所需的最小部分，而没有引入 Puppeteer。没装浏览器时该项自动跳过。

配合的是三处让错误可见的改动。`refreshState()` 的 catch 现在会把 `Error` 实例重新抛出：`fetchJson` 抛的是后端返回的 JSON 对象，从不抛 `Error`，所以真正的 `Error` 一定是代码缺陷而非网络故障，不该被伪装成"加载失败"。`app.js` 除启动兜底外，还监听了 `error` 与 `unhandledrejection`——`render()` 几乎被所有交互调用，它在 async 回调里抛出的错误会变成静默的 promise rejection，界面已死而控制台无声。

`FrontendBehaviorTests` 里只有真正求值 JS 的用例依赖 quickjs，跳过标记因此下放到方法级。另外 12 个用例只断言产物源码，没有 quickjs 也应当运行——原先的类级标记把它们一起跳过了，恰好掩盖了本次重构引入的两处过期断言。quickjs 在没有 C 编译器的 Windows 上装不上，这批用例会跳过属于预期。

注意：测试必须从项目根目录运行。回放目录 `replays/` 使用相对路径，从 `tests/` 目录运行会有个别用例失败。
