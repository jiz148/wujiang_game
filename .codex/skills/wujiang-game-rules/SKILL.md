## Mandatory Workflow

1. Read `references/project-map.md` at the start of any hero, rule, battle-engine, or gameplay UI task.
2. Read `docs/产品开发路线图.md` before planning or implementing any new player-visible feature. Treat its active Phase, pause list, exit gates, and definition of done as the default product priority. Do not implement a later-Phase feature unless the user explicitly overrides the roadmap, or the work is a rule/stability/security fix allowed by the roadmap. Update the roadmap when Phase status, scope, gates, or priority changes.
3. Read `references/hero-rule-index.md` when the task involves a specific hero, skill, trait, or current implementation lookup.
4. Consult the repo docs before coding. Prefer `docs/通用规则.md`, `docs/通用技能和特性说明.md`, `docs/武将说明.md`, and `docs/武将游戏规则.md`.
5. Use a strict design-first workflow for every new hero and every review/debug pass over an implemented hero. The mandatory order is: source rules and durable clarifications -> independent design interpretation -> recorded/locked design baseline -> battle-code review -> AI-code review -> test review -> defect classification -> modification. During the design-interpretation pass, do not inspect or use the current hero implementation, AI code, or tests to infer what the design was supposed to mean. Existing code is evidence to compare later, never a source of design truth.
6. Before inspecting that hero's code, record a detailed per-hero design baseline in the `武将设计思想` sheet of `docs/武将实现问题清单.xlsx` and synchronize the same baseline to `docs/武将设计思想.json`. Record at least: battlefield role and player fantasy; core design intent and meaningful player decisions; intended operation sequence and resource/action cadence; skill/trait synergy; intended strengths, weaknesses, and counterplay; AI priorities and sequencing; general-AI lessons; behaviors the AI must avoid; timing, targeting, lifecycle, and interaction boundaries; expected observable signals; risk patterns; source clarifications; and ambiguities. When source text and durable rules do not uniquely resolve an ambiguity, infer the interpretation that best preserves the hero's coherent design intent instead of pausing for user answers. Record the chosen interpretation, rejected alternatives, evidence, confidence, and gameplay consequences. Never infer from current code or tests.
7. Only after the design baseline is recorded may the agent inspect battle code. Map every source clause and design expectation to concrete implementation behavior: target/range/selection, cost, limits/cooldowns, timing/order, damage/effects, status lifecycle, summons/clones, chain reactions, frontend preview, public state/logs, and relevant common-rule interactions. Record whether each item conforms before changing it.
8. Review AI only after the battle-code comparison. Check both hero-specific and general AI for payload generation, target choice, action sequencing, resource conservation, skill synergy, reaction choice, prohibited behavior, and opportunity utilization. "The skill appeared at least once" is not sufficient; compare opportunities, selections, outcomes, and strategic value against the recorded design intent.
9. Derive the test matrix from the locked design baseline, then inspect existing tests. Every key rule, boundary, intended decision, and conditional lifecycle must have deterministic coverage. Write or update missing targeted and behavior tests, but do not use current tests as a substitute for understanding the design.
10. For new heroes, finish or update documentation before coding. Keep `docs/武将实现问题清单.xlsx` as the structured ambiguity inventory for unimplemented Excel heroes, with one row per concrete rule question and at least: hero name, module/skill/trait/front-end area, question id, question text, alternatives, any preserved user answer, and notes/source context. Do not pause for new user answers. For each selected hero, resolve every unanswered row through the source-only design-baseline process and record the inferred answer plus rationale, rejected alternatives, confidence, and gameplay consequences in the design archive before implementation.
11. The questionnaire must preserve ambiguity quality and quantity. Do not reduce the number of ambiguity questions just because the format is Excel. Include all rule, timing, targeting, effect-order, stacking, summon/clone, resource, AI, frontend selection/preview, and player-facing UI questions needed so that after the user answers the workbook, each listed hero has no remaining ambiguity before implementation. Do not include questions that merely ask whether durable/default/common rules apply; those rules apply automatically. Do not include base-stat confirmation, common skill confirmation, common trait confirmation, generic skill/trait split confirmation, or generic team-stat adjustment confirmation unless the source row contains hero-specific extra text that creates implementation ambiguity. Do not generate questionnaire rows from broad keyword templates such as "resource", "duration", "summon", or "frontend"; each question must be tied to a specific hero text ambiguity and should match the style of the prior one-hero clarification passes, with concrete rule alternatives rather than repeated generic implementation categories.

Once every material question for the selected batch is resolved one way or the other, implement from the workbook, durable rules, and recorded design baselines, keeping docs, code, frontend previews, AI, and tests synchronized.

## Implementation Priorities

- Treat user clarifications as authoritative game rules.
- Preserve existing user changes in the working tree; do not revert unrelated files.
- Use `apply_patch` for file edits.
- Prefer reusable engine hooks for general mechanics before adding hero-local special cases.
- For grid/range/targeting changes, check backend legality, frontend preview/click selection, and reaction-window target discovery together.
- Treat AI behavior as part of the implementation surface. When fixing a hero, also inspect and update general AI payload generation/scoring and any hero-specific AI logic needed for that hero to use, target, chain, and avoid wasting its mechanics correctly.
