# wujiang_game Project Map

Update this file after every new gameplay requirement or code change in `wujiang_game`. Keep entries concise and durable; do not paste full docs.

## Current Layout (read this before using any path below)

The codebase was reorganised by domain on 2026-08-27. Every phase record further down still cites the pre-reorganisation paths (`web/server.py`, `strategy/*.py`, `engine/core.py`, `static/app.js`). Those records describe what was true when they were written and are deliberately left unchanged; use the map below to translate them.

- `src/wujiang/platform/` — HTTP kernel (`http/handler.py` dispatch, `http/runtime.py` shared stores, `http/routing.py` route registry, `http/server.py` composition root), plus `auth.py`, `analytics.py`, `match_history.py`, `observability.py`, `rate_limit.py`, `security.py`, `deployment.py`. Contains no gameplay knowledge and must never import `tactical` or `strategic`.
- `src/wujiang/tactical/` — `engine/` (was `engine/`), `heroes/` (was `heroes/`), `rooms/` (was `web/multiplayer.py`, `ai.py`, `replay.py`, `postgame.py`, `tutorial.py`, `onboarding.py`, plus new `rooms/history.py`), `session.py`, and `api.py` for the 34 battle routes.
- `src/wujiang/strategic/` — everything that was `strategy/`, plus `campaign_runtime.py` (campaign store singleton and shared helpers), `service.py` (order validation, command accounting, action queue; was inline in `web/server.py`) and `api.py` for the 31 campaign routes.
- `src/wujiang/bridge/battle_bridge.py` — the only channel between the two game domains: campaign conflict to grid room, and battle result back to campaign state. `tactical` and `strategic` must not import each other.
- `static/` mirrors the split as native ES modules: `core/`, `platform/`, `tactical/`, `strategic/`, and `bridge/campaign-battle.js`. `app.js` is now a 34-line entry point. `home-ui.js`, `replay-ui.js` and `battle-feedback.js` moved under `platform/` and `tactical/` but remain classic scripts using their `globalThis.Wujiang*` namespaces, because the quickjs behaviour tests evaluate them directly.
- Routes are registered per domain with `@get` / `@post` from `wujiang.platform.http.routing`; the kernel owns dispatch only, and `platform/http/server.py` assembles the app by importing the three `api` modules. Readiness dependencies register themselves via `register_dependency`.
- Frontend assertions now read the whole of `static/` through `frontend_source()` / `frontend_module()` in `tests/test_behavior.py`, so moving code between modules is no longer a test failure. `tests/test_frontend_modules.py` plus `tools/verify_frontend_modules.mjs` link-check the real module graph and enforce that the two frontend domains stay independent.
- Screens are a first-class concept in `static/core/router.js`: `gate`, `menu`, `draft`, `battle`, one visible at a time, each backed by `#<name>-screen`. Login is a hard gate — `render()` short-circuits to the gate screen when logged out, matching the backend, which already 401s every gameplay POST. The main menu deliberately has no single/multiplayer split: every session has slots, AI holds the empty ones, and humans can take over, join late or spectate.
- The address bar names the destination, never the container. `draft` hosts four unrelated flows (`campaign`, `skirmish`, `tutorial`, `archive`), so a `#draft` hash says nothing about where the player is — and the old `screenHash()` wrote it for every non-battle screen including the menu, so the next visit skipped the menu and dropped into whichever flow was default. Flow names double as hashes; `routeTarget()` sends anything unrecognised to the menu.
- Campaign and skirmish sit side by side in the menu. The axis is whether you run a map, not how many humans play: skirmish creates rooms and invite codes too. Its three entries used to be split across two unrelated flows, so nobody could tell they led to the same thing.
- Copy belongs to the markup. `hydrateStaticLabels()` used to rewrite twenty-odd labels at boot that `index.html` already stated, so new button text would silently revert to the old wording.
- `static/theme.css` holds the design tokens, base reset and component layer (`.btn`, `.input`, `.field`, `.panel`, `.tabs`, `.chip`, `.hint`) and must load before `styles.css`, whose tail aliases the legacy token names onto the dark ones. `static/core/components.js` is the matching JS factory, since the UI is built imperatively and CSS classes alone do not enforce consistency.
- A module must not write shared chrome unless it owns the current screen; `renderRoomPanels()` used to overwrite the page header even while the player was in a campaign. The topbar now belongs to `static/core/topbar.js`; it used to be `renderNavigation()` in the tactical domain.
- Show nothing until the destination screen is known. Some screen has to be visible in the markup and it is not necessarily the one the player lands on, so the page flashed the room lobby before jumping to the menu. `body.is-booting` keeps the shell `visibility: hidden` until `applyScreen()` runs — and the failure path must clear it too, or the error banner hides with it.
- A room is something you are looking at, not a standing identity. The lobby shows whenever a room is in hand regardless of flow, so a stale `?room=` in the URL covers whatever you picked from the menu — picking campaign lands you in a skirmish room. `leaveRoomView()` (`tactical/session.js`) drops the room from view on every menu departure; the server-side room and the stored seat identity survive, reachable via `#room-directory` on the skirmish screen or the invite link.
- Side-by-side buttons cannot express priority. `createMenu()` collapses secondary actions so the remaining one carries weight; `createMenu({ children })` adopts existing buttons, keeping their IDs, listeners and `.hidden` toggles. Two traps: `[hidden]`'s `display: none` comes from the UA sheet and loses to an author `display: flex`, so `.menu__list[hidden]` must restate it or the popover never closes; and adopted buttons carry `.ghost`/`.btn` borders, so `.menu__item` needs the `.menu__list` prefix to win.
- Do not name lookup-able nodes through `createMenu`'s `id` option — `verify_frontend_dom_ids.py` reads `.id = "..."` assignments, and treating every `id:` option literal as a known DOM ID would gut the check. Assign `node.id` explicitly.
- Put a hint's `id` on `.hint__bubble`, not the outer `.hint`: existing code writes `note.textContent`, which would erase the icon and structure.
- Prose earns its place only if it can change the reader's next move. Two failure modes were everywhere in the campaign screens and are worth recognising by shape. **Always-true captions**: "邀请已锁定 · 当前账号可直接恢复" printed on every card, or a three-line status strip whose three lines all mean "this campaign has started" — text that is identical in every state carries no information. **Restating the widget**: "点击城市选择命令目标", "选择一个战役后会显示城市、科技和事件", "行动队列为空" next to a visibly empty queue. Rules and read-once explanations belong in a `createHint()` bubble; per-item facts stay inline; sections with nothing to report should not render their heading at all (see `renderStrategyRecoveryOverview`, which used to draw a title plus "可恢复 0 场…" plus "还没有检查点"). Same for permanently-disabled buttons — "推进一月" on the campaign list has no month to advance, so it hides rather than sitting greyed out.
- `tools/verify_frontend_boot.py` drives Chrome over CDP (`tools/cdp.py`, standard library only) through gate, menu, campaign list, live campaign, skirmish and battle, and asserts each screen's hash. Walk all the way through: each screen is reachable only via the one before it, so a screen no check opens is a screen that breaks unnoticed. The live campaign is its own step because it shares almost no code with the list that leads to it -- assigning to an SVG's read-only `className` crashed the whole map while the list still looked fine, so every check passed and the screen behind the button rendered nothing. That step also asserts the campaign screen does not exceed the viewport. Snapshot flags like `--dump-dom` fire before the app finishes awaiting `/api/auth/me`, so they always capture the login gate.
- Campaigns can be deleted, not just archived. Archiving means "this run is over, keep it for the retrospective"; archived campaigns stay in the list, so with only archive the list could never be cleaned up. `delete_campaign` is owner-only and deletes one `strategy_campaigns` row — every child table declares `ON DELETE CASCADE` and the connection sets `PRAGMA foreign_keys`, so they follow. The audit log is deliberately exempt: it is a hash-chained append-only log with no foreign key on `campaign_id`, and removing entries would break the chain. Write the audit row *before* the delete — `_audit_operation` looks the actor's username up in `strategy_members`, which is about to be cascaded away.
- A button whose only effect is invisible reads as broken. "离线" always called `mark_offline` correctly, but the campaign card never showed presence, so clicking it changed nothing on screen. It now appears only while you are actually online and disappears once clicked.
- `core/dialog.js` `confirmDialog()` returns `Promise<boolean>` and replaces `window.confirm` for destructive actions (delete campaign, delete room, leave room, surrender, log out). Native confirms look nothing like the app, cannot reword their buttons, and block the page. Focus defaults to Cancel; the `keydown` listener is on the capture phase so global shortcuts (space to pause, arrows to pick cells) do not fire while it is open.
- The account menu holds exactly three items: profile, back to main menu, log out. "Room lobby" used to be there too but its visibility condition was identical to the contextual primary button beside it, and "copy invite" already lives in the room header overflow. Dropdown item heights must be set by `.menu__list .menu__item` (fixed `min-height` + `line-height: 1`), never inherited: adopted buttons carry `.btn` / `.primary` / `.ghost` padding and end up uneven.
- Campaign screen shape lives in `static/strategic/campaign-shell.js`: hero rail left, map centre, inspector right, month bar bottom. `body.campaign-mode` (the one-viewport lock) applies only once `status === "active"`; during lobby the screen still stacks the origin-choice panel, lock banner and lock button above the war room, and locking the height would subtract all of that from the map. In lobby the three columns instead get a height band plus `grid-template-rows: minmax(0, 1fr)` -- max-height alone does not work, because an `auto` row track sizes to the tallest column's content and simply overflows the capped container. Two more traps. Buttons cannot be *moved* into the turn bar -- `#strategy-current` is cleared with `innerHTML = ""` on every render, which would delete them; the bar creates its own and forwards clicks, copying the disabled state so the judgement stays in one place. And locking the screen to one viewport needs the whole chain flexible: `.shell` at `height: 100vh` plus `display: flex` + `flex: 1 1 auto` + `min-height: 0` on `#draft-screen`, `.draft`, `#room-home` and `.strategy-panel`. Missing `display: flex` is the subtle one -- the parent offers a height but a plain block child never looks at it.
- `tools/verify_frontend_dom_ids.py` catches `$("...")` lookups whose element was deleted from the markup — invisible to every other static check, and it surfaces at runtime as a caught `null` error that freezes a button with a clean console.
- Colour literals do not follow the token remap. When something still looks light, it is hardcoded: sweep it into a token rather than patching the one rule.
- No gradient backgrounds on chrome; gradients are reserved for game surface and signal (pieces, mana pips, battle VFX, colourblind hatching, the strategy map). Nested frames are flattened too: `#room-home > *` strips borders from the flow panels because the outer `.draft.panel` already provides the panel feel. The id selector is deliberate — the panels' own border declarations sit later in `styles.css` and win at equal specificity.
- Full regression after the reorganisation is 767 passing with 26 environment skips. Run tests from the repository root; `replays/` is resolved relative to the working directory.
- Full layering rules and rationale: `docs/架构分层说明.md`.

## Current Engine Patterns

- Durable default conventions: do not ask again when these apply. If an active skill has no cost text, it costs 0 mana; if any skill has no use limit/cooldown text, it has no use-count limit; if a damaging skill/area has no fixed `伤 n` and no `没有伤害`, use current attack; if no `破魔` text, it does not pierce shields; if no ally/enemy qualifier, it affects both sides; `单位` includes heroes, summons, and clones; `武将` means non-summon non-clone hero body only; stat reductions to attack/defense/speed/range floor at 1; modifying the `mana` stat means both max mana and current mana are modified then clamped.
- Durable targeting wording: `周围` without extra text means the 8 cells at distance 1 around the unit's occupied cells, excluding its own occupied cells; `攻击` without extra text means basic attack / 普攻, not skills.
- Durable direct-unit targeting rule: skills that directly select one or more units must select targets both within the caster's `范` (or the skill's own written point-unit range, such as `范 5`) and along a horizontal, vertical, or diagonal line from any caster occupied cell to any target occupied cell, unless the skill explicitly overrides this. - Durable magic-immunity definition: `魔免` prevents enemy skill damage and enemy skill follow-up effects, but not basic attacks, weather, or field effects.
- Durable common-entry default: if a hero writes a known common skill or trait and adds no extra rule text, implement it exactly as the common version without asking again.

- Durable sheet/default wording: Excel `炎` maps to the existing `火` attribute. Non-square areas such as `3*6` that do not say `身前` are remote range-based rectangles and can be placed in either orientation. Text like `攻击带有以下破魔效果` or `带有破魔的 X 效果` makes only the listed / named follow-up effect piercing, not the whole attack or skill.
- Durable passive-text default: only skills whose text starts with / explicitly says `被动技能` are passive chain skills. Other skills are not passive unless they say `随时使用` or another timing rule.
- Durable ultimate-prefix default: skills prefixed with `￥` or `¥` are big moves / ultimates. They default to once per battle unless the skill text writes a different use count, cooldown, or reset.
- Durable passive-trigger default: passive skills without extra support/protection/other trigger wording can only chain when their owner is about to be affected by an enemy action.
- Durable magic-point default for new heroes: if a future hero has a magic-point mechanic and no explicit initial magic-point value, its initial magic points equal its base mana.
- Durable n-v-n timing rule: one turn belongs to one hero, not one player. One player may control multiple heroes, but only one hero acts in a turn. A hero's `己方回合` means that hero's own turn, and one `轮` for that hero runs from its own turn start to its next own turn start.
- Durable start-phase / toggle rule: each hero turn has a start phase. Resolve start-of-turn effects first, then in that same start phase ask whether to use start-phase toggle skills. Toggle skills alternate open/close on each use and become unavailable after normal movement, attacks, or other active actions.
- Durable cannot-act rule: `不能行动` means the unit cannot normal move, cannot basic attack, cannot use active skills, and cannot use passive chain skills.
- Durable split-movement rule: `没有移动次数限制` means a unit may split normal movement into any number of normal moves, but total normal movement distance in that turn still cannot exceed current speed.
- Durable ordered-path rule: normal movement submits a full ordered adjacent-cell path. Within the current speed budget it may turn, backtrack, return to its origin, and repeat cells. A pass-through trigger counts entry into a unit footprint; continuous overlap across several cells of a multi-cell unit is one crossing, and a new crossing requires fully leaving that footprint before re-entry.
- Durable extra-move-count rule: `每回合移动次数 +1` grants one extra normal-move action per turn; each normal move is still separately capped by current speed.
- Durable round-duration rule: if docs/rules say an integer `持续 N 轮` for a unit status or integer-round local effect, count it on the affected unit's or owner's own round boundary, not on every global hero turn. Half-round effects such as `1.5轮` / `2.5轮` still need explicit per-skill handling.
- Durable passive-count rule for n-v-n: passive/reaction skills written as `每回合最多 X 次` reset separately in each opposing hero turn, not once per whole round. - Run targeted tests for the changed rule first.

- Run `python -m unittest discover -s tests` before final response when feasible.
- `git diff --check` may show LF/CRLF warnings on this Windows repo; treat actual whitespace errors separately from those warnings.
